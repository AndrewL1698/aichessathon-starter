# k4-v44-e4 — the first genuinely fine-tuned four-bucket net

`weights/nnue.npz` on `nnue/king-buckets-4-v44`, sha256
`6dc6f42325d17a2700cb3d42b61b109890c5972759bd0e08d30de6110b1a1808`, 1,083,502 bytes. Branch
based on `origin/prod` **83cd33b** (engine v4.4, tag f96597d). **Not benched. Not merged.**

## Data

`tools/nnue/data/lichess-48m`, the corpus that trained the shipped net: 180 shards, exactly
**90,000,000 rows** (51,687,780 unique positions plus 38,312,220 mirrors), `indices` int16
[N,32], `cp` int16 clipped to +-2000, `wdl` int8. Verified on arrival: every shard scheme-1 with
no marker, active index range [8, 767], cp range [-2000, 2000], exactly one plane-5 friendly-king
feature per row, no anomalies.

Converted with `tools.nnue.rebucket` into `tools/nnue/data/lichess-48m-k4` — **no relabelling,
no re-ingestion**; the originals' hashes are unchanged and `cp`, `wdl`, row order and shard
boundaries are identical, with every index equal to the original modulo 768. Bucket spread over
all 90M rows:

| bucket | rows | share |
|---|---|---|
| 0 own half, queenside | 35,862,837 | 39.85% |
| 1 own half, kingside | 48,278,065 | 53.64% |
| 2 far half, queenside | 2,929,470 | 3.25% |
| 3 far half, kingside | 2,929,628 | 3.26% |

### The deviation: 30M rows, not 90M

**The run trained on 60 of the 180 shards, every third one, 30,000,000 rows.** This machine has
16 GB and could not hold the full index matrix: the concatenating loader peaked near 12 GB and
put 27 GB into swap, the preallocating loader still needed 5.8 GB resident and went backwards at
0.8 GB and falling, and memory-mapping the full matrix left the first epoch disk-bound at
5.5 MB/s, about 17 minutes of I/O per epoch. Every third shard was chosen so the subset spans the
whole byte range the corpus was built from rather than its first third, and it preserves the
bucket spread almost exactly: **39.71 / 53.69 / 3.30 / 3.30**, with bucket 2 at 990,226 rows and
bucket 3 at 990,332. Both loader fixes are committed and the full 90M run is a machine with more
memory away, not a code change.

## Initialisation

No float checkpoint of the shipped net exists on this machine, so `tools.nnue.dequantize` rebuilt
one from `weights/nnue.npz` at v4.4 (sha256 `fc7c862f...`): each layer divided by the scale the
export multiplied it by. The rebuilt model reproduces the shipped net to **1.40 cp mean, 6.49 cp
worst** over 2,000 positions, against the 5 / 25 gate `test_export` holds the other direction to.
Because the runtime expands a scheme-1 file into four identical blocks, the checkpoint is
3072 x 256 directly and is the warm start; sha256
`a34780f0d4eee9295ec8ff0decfd940ff4bc017115adb7205c3db199bafd11fb`.

## The run

```
uv run python -m tools.nnue.dequantize --weights weights/nnue.npz \
    --out tools/nnue/checkpoints-dequantised/epoch_000.pt
uv run python -m tools.nnue.rebucket --data tools/nnue/data/lichess-48m \
    --out tools/nnue/data/lichess-48m-k4
uv run python -m tools.nnue.train --data tools/nnue/data/lichess-48m-k4-30m \
    --checkpoints tools/nnue/checkpoints-k4-clip19 --hidden 256 --epochs 8 --batch-size 8192 \
    --lr 3e-4 --cp-scale 400 --target cp --seed 1 --val-fraction 0.02 --patience 3 \
    --min-delta 1e-5 --l1-clip 1.9 \
    --init-checkpoint tools/nnue/checkpoints-dequantised/epoch_000.pt
uv run python -m tools.nnue.export --checkpoint tools/nnue/checkpoints-k4-clip19/epoch_004.pt \
    --out weights/nnue.npz --qa 512 --qb 1024
```

MPS, 29,400,000 training rows and 600,000 validation rows, mean-predictor baseline 0.056202.

| epoch | train | val | seconds |
|---|---|---|---|
| 1 | 0.014099 | 0.013878 | 442.9 |
| 2 | 0.013615 | 0.013808 | 120.5 |
| 3 | 0.013359 | 0.013780 | 82.7 |
| **4** | 0.013182 | **0.013776** | 81.3 |
| 5 | 0.013048 | 0.013778 | 101.4 |
| 6 | 0.012941 | 0.013790 | 90.6 |

Stopped by `--patience 3 --min-delta 1e-5` after epoch 6; **best epoch 4**. 919 s of epochs,
about 16 minutes end to end. No NaN, no divergence, no memory failure.

### The other deviation: l1 clip 1.9, not 3.8

The configured `--l1-clip 3.8` was run first and reached a slightly better validation loss
(0.013735 at epoch 4) -- **and could not be exported.** A clip of 3.8 puts the largest layer-1
weight exactly on the bound, which forces qa=256 (at qa=512 the worst accumulator is 50,997
against int16's 32,767), and at qa=256 the export missed the project's own quantisation gate:
**4.29 cp mean, 28.90 cp worst against a 25 cp limit.** Raising qb did not help -- 2048 gave
29.21 and 4096 gave 28.90 -- because the error is layer-1 precision, not layer-2. A clip of 1.9
is what `train.py`'s own docstring says "always exports at qa=512", and it does. The cost is
4.1e-5 of validation loss; the benefit is an exportable net.

## Selection checks

- all four buckets represented: 39.71 / 53.69 / 3.30 / 3.30 percent, the rarest at 990,226 rows
- first-layer blocks no longer identical: pairwise mean |diff| 0.0475 to 0.0496, no pair equal
- sanity at epoch 4: **start +35cp, +1 pawn +98cp, +1 rook +423cp, mate in 1 +1783cp** — signs
  and material ordering correct
- no NaN or inf in any tensor; max |l1 weight| exactly 1.900, the clip

## What this is not

It is not a strength result. Validation loss is not comparable with the shipped net's 0.014602,
because that was measured on the 90M split and this on a 600k split drawn from 30M rows, and
cycle 7 in `docs/BENCH_LOG.md` is the standing reminder that validation loss has twice failed to
order these nets on the board. The only thing that decides this candidate is a bench against
`local-opponents/v4.4` at both controls, and it has not been run.
